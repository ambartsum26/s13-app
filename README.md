# Ассистент по участкам

Небольшое браузерное приложение для ведения городов, участков, истории выдач и базы возвещателей с хранением данных в Firebase Firestore.

## Структура

- `index.html` — базовая HTML-разметка и минимальные fallback-стили.
- `app.js` — точка входа и подключение модулей.
- `app-core.js` — Firebase-данные: города, участки, возвещатели, выдача/сдача и история.
- `app-data.js` — транзакционное сохранение истории и защита от одновременного создания дубликатов.
- `app-auth.js` — авторизация владельца через Firebase Authentication.
- `app-ui.js` — общий внешний вид и компоновка приложения.
- `app-cards.js` — оформление и поведение карточек участков.
- `app-popups.js` — модальные окна, Esc, закрытие по фону и блокировка прокрутки.
- `s13-export.js` — экспорт регистра S-13.
- `firestore.rules` — серверное ограничение доступа к Firestore по UID владельца.
- `tests/auth.test.cjs` — проверки логики авторизации без обращения к рабочей базе.
- `.github/workflows/auth-check.yml` — автоматический запуск auth-тестов на push в `main` и в pull request.
- `.gitignore` — исключает локальные `.env`, Firebase CLI-файлы, `node_modules` и системный мусор.

## Принцип изменений

Данные Firestore изменяются только через явные действия пользователя в `app-core.js`, включая вызовы `app-data.js`. UI-модули не должны удалять, переносить или переписывать данные базы самостоятельно.

Перед крупными изменениями рекомендуется создавать резервную ветку GitHub. Не менять названия коллекций `cities`, `territories` и `publishers` без отдельной миграции данных.

## Вход владельца

Пользовательский интерфейс входа работает в режиме **только пароль**. Технический e-mail владельца хранится в `app-auth.js` и автоматически передаётся Firebase Authentication; пользователь его не вводит. Сам пароль не хранится в GitHub, `localStorage` или Firestore.

Приложение не начинает чтение Firestore, пока Firebase Authentication не подтвердит UID владельца. После выхода активные подписки Firestore отключаются, открытые формы закрываются, а загруженные данные удаляются из интерфейса.

Сеанс использует `browserSessionPersistence`: он переживает обычное обновление страницы в текущей сессии браузера, но не является постоянным входом на неопределённый срок.

### Что должно быть настроено в Firebase

1. В **Authentication → Sign-in method** должен быть включён провайдер **Email/Password**.
2. В **Authentication → Users** должен существовать технический пользователь, используемый `app-auth.js`.
3. UID этого пользователя должен совпадать с UID в `app-auth.js` и `firestore.rules`.
4. Web API key в конфигурации Firebase должен относиться к этому же Firebase-проекту и разрешать запросы Firebase Authentication / Identity Toolkit.
5. `firestore.rules` нужно публиковать отдельно в Firebase/Firestore. GitHub Pages сам правила Firestore не разворачивает.

Если Firebase возвращает ошибку входа, `app-auth.js` показывает безопасный код `auth/...` и не выводит пароль, e-mail или полный объект ошибки в консоль.

## Защита Firestore

`firestore.rules` разрешает чтение и запись только авторизованному пользователю с UID владельца. Проверка UID в JavaScript является дополнительной защитой интерфейса и не заменяет серверные Firestore Rules.

Не ослабляйте правила до `allow read, write: if true` даже временно на рабочей базе.

## Проверки

Локальная проверка без обращения к рабочей базе:

```bash
node tests/auth.test.cjs
node tests/data.test.cjs
node tests/export.test.cjs
node tests/publisher-sort.test.cjs
```

Тесты проверяют password-only вход, использование введённого пароля, блокировку до входа, отказ чужому UID, выход, безопасную диагностику Firebase API key, очистку данных интерфейса и остановку подписок после выхода.

GitHub Actions автоматически проверяет синтаксис модулей и запускает все четыре набора тестов при каждом push в `main` и для pull request. Проверки данных используют модель оптимистических транзакций без подключения к рабочей базе; проверяют конфликтующие выдачи, редактирование и удаление, дубликаты, совместимость старых записей и сохранение DOM неизменённых карточек. Экспорт проверяется на границах служебного года и при заполнении дополнительных листов. Реальные Firestore Rules и реальный Firebase Authentication дополнительно проверяются в Firebase Console/эмуляторе.

## Одновременная работа и старые данные

История сохраняется транзакцией по актуальному документу участка. Изменения других записей сохраняются; если изменена именно редактируемая запись, приложение предлагает открыть её заново. У записей появляются постоянные `id` при следующем явном сохранении истории. Массовая миграция при входе не выполняется. Неоднозначные одинаковые старые записи блокируют адресное редактирование/удаление до разрешения неоднозначности, чтобы не затронуть чужую строку.

Для уникальности используются служебные документы `appLocks`: один для возвещателей и по одному для каждого города. Все добавления, переименования и удаления в соответствующей области читают и обновляют этот документ внутри транзакции. Проверка существующих имён/номеров читает сервер после чтения блокировки; конкурентная операция вызывает повтор транзакции вместе с этой проверкой. Это учитывает старые документы без отдельного индекса имён. Правила из `firestore.rules` разрешают владельцу доступ к этой коллекции; если на сервере установлены другие, более узкие правила, нужен такой же доступ только для UID владельца.

После обновления нужно перезагрузить ранее открытые вкладки на всех устройствах: старые версии приложения не используют транзакционную защиту. Транзакционные операции требуют подключения к интернету. Защита уникальности рассчитана на запись через новую версию приложения; прямые изменения в Firebase Console и старые клиенты обходят её. Существующие дубликаты автоматически не удаляются.

## Экспорт S-13

При экспорте выбирается служебный год: например, 2027 означает 01.09.2026–31.08.2027. Граница года соответствует [определению на jw.org](https://www.jw.org/en/jehovahs-witnesses/faq/how-many-jw/). В выбранный год попадают выдачи, пересекающие этот период, включая незавершённые выдачи предыдущих лет; показываются их фактические даты. В первой колонке сохраняется последняя сдача до начала периода, а на продолжениях — до соответствующей группы выдач. После четырёх выдач создаются дополнительные листы. История в базе при экспорте не изменяется. Некорректные даты требуют исправления перед экспортом и не пропускаются молча.

## Резервные копии и секреты

Пароли, резервные выгрузки Firestore и другие чувствительные данные нельзя сохранять в публичном репозитории. Firebase Web API key сам по себе не является паролем, но его ограничения должны быть настроены корректно в Google Cloud/Firebase.
