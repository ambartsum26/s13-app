# Эксперимент: сквозное шифрование для «Участков» (E2EE)

**Статус:** только прототип в ветке prototype/e2ee-single-custodian-20261017.
**Ничего не внедрено в действующее приложение.** Данные Firestore, Authentication,
security rules, production bundle и работающий экспорт S-13 не изменены.

## Принятый принцип доступа

- Для каждой группы назначен **один** ответственный за участки.
- У каждой группы — **свой 256-битный ключ** для конфиденциальных данных.
- Администратор платформы не получает ключи чужих групп автоматически.
- Секрет восстановления хранится **вне Firebase, GitHub и основного устройства**;
  ответственному необходимо хранить его отдельно от зашифрованного пакета
  восстановления. В прототипе оба компонента нужны для восстановления.
- При смене ответственного нужны безопасная передача прав и ротация ключа.
  Это пока **не реализовано**.

## Что реализовано в изолированном модуле

Файл e2ee/crypto.js использует только встроенный Web Crypto API:

1. Генерирует случайный 256-битный ключ группы и независимый случайный
   256-битный секрет восстановления.
2. Импортирует ключ группы в виде **неэкспортируемого** AES-256-GCM CryptoKey.
3. Шифрует исходный ключ группы в пакете восстановления AES-256-GCM с отдельным
   ключом, полученным из высокоэнтропийного случайного секрета через HKDF-SHA256.
   HKDF подходит именно для случайного 256-битного секрета, **не для
   пользовательского пароля**.
4. Шифрует отдельные документы с новой случайной 96-битной nonce и 128-битным
   authentication tag. Контекст группы/коллекции/ID документа включён в AAD,
   поэтому перемещение зашифрованной записи между группами или ID не должно
   проходить аутентификацию.
5. Расшифровывает документ и восстанавливает неэкспортируемый ключ по корректному
   секрету восстановления и пакету восстановления.

**Экспериментальные функции:** createGroupVault, recoverGroupVault,
encryptDocument, decryptDocument. Они **не импортированы** из app.js
и **не подключены** к живой базе.

## Разделение групп (только эмуляторы)

Экспериментальный файл правил: `e2ee/prototype.rules`. Он **не является**
`firestore.rules` рабочего Firebase и не должен публиковаться в production.

- Идентификаторы групп: `e2eeGroups/{groupId}`.
- Каждая группа содержит идентификатор **одного** ответственного
  (`custodianUid`) и поля `schemaVersion: 2`, `status`, `revision`,
  `handoverId`. В браузере создание/смена владельца **запрещены**.
  Новое состояние `frozen` блокирует изменения документов и пакета
  восстановления для обычных клиентов, сохраняя доступ на чтение
  старому ответственному до окончательного переключения.
  Доверенная процедура регистрации групп ещё не разработана.
- Зашифрованные записи находятся по путям
  `e2eeGroups/{groupId}/territories/{documentId}` (также
  `cities`, `publishers`, `addressMarkers`). Имена полей открытых документов
  в этих путях не принимаются: допустим только конверт шифротекста.
- В `e2eeGroups/{groupId}/recovery/current` допускается зашифрованный
  пакет восстановления. **Резервный код туда не помещается.**
- Чтение/запись записей доступно только назначенному ответственному,
  перечисление всех групп, удаление истории и создание группы через клиент
  запрещены.

Сценарий `e2ee/test-emulator.mjs` создаёт **только вымышленных**
пользователей и группы в локальных эмуляторах Firebase Authentication и
Firestore, проверяя отказы в доступе между группами и после выхода.

Для запуска: `npx firebase emulators:exec --config e2ee/firebase-prototype.json --only firestore,auth --project demo-s13-e2ee "node e2ee/test-emulator.mjs"`.

**Важно:** криптографическая аутентификация не отменяет серверную проверку
разрешений. Отдельно предстоит проверить создание групп, изменения прав,
сценарий передачи полномочий и согласованную политику удаления записей.

## Прототип работы с участками и S-13 (без production)

- Файл e2ee/territory-service.js — изолированный прикладной адаптер:
  поиск возвещателей после локальной расшифровки, список участков по городу,
  выдача/сдача с проверками истории, подготовка данных S-13 за выбранный
  служебный год. Ничего не записывает в действующий Firebase.
- Файл e2ee/firestore-transport.js — отдельный транспорт для
  экспериментальных путей e2eeGroups/{groupId}: читает актуальные
  документы с сервера, исполняет выдачу/сдачу в Firestore-транзакциях,
  проверяет UID перед выполнением запроса. **Правила доступа сервера
  остаются обязательными**.
- В одном запросе выдачи транзакция читает зашифрованные документы участка
  и возвещателя до записи, затем расшифровывает оба на клиенте и записывает
  новый шифротекст. Это предотвращает молчаливую перезапись при конкуренции
  двух выдач; сервер по-прежнему не проверяет смысл зашифрованной истории.
- Участки загружаются внутри группы и фильтруются по городу **на клиенте**
  после расшифровки. Имена, даты и cityId не используются для открытых
  Firestore-запросов.
- prepareS13 подготавливает локально расшифрованную модель для
  существующего механизма форматирования S-13. Он **не экспортирует файл**
  и не интегрирован в рабочую кнопку. Сам скачанный .doc содержит открытые
  сведения: защищать экспортированный файл обязан ответственный.
- Тест tests/e2ee-service.test.cjs проверяет одновременные выдачи,
  сдачу, срок до повторной выдачи, поиск, пересечение служебных лет,
  повреждённые данные и совместимость с существующим S-13-рендерером.
  Это только **синтетические данные**.
- Эмуляторный тест дополняет проверку действий реальными Firestore-
  транзакциями и серверными правилами, также без production-доступа.

**Остаётся выполнить до реального внедрения:** безопасную регистрацию новых
групп; политику уникальности номеров и возвещателей при зашифрованных
индексах; передачу полномочий одному новому ответственному и ротацию
ключа; управление локальным ключом при входе/выходе; обработку
конкурентного редактирования всех полей; резервное восстановление и
полную проверку совместимости с UI. Потребуется независимая проверка
криптографического решения и согласование миграции.

## Прототип входа, блокировки и смены ответственного

- **e2ee/session.js** хранит расшифрованный AES-ключ только в памяти сеанса.
  После Firebase-входа ответственный отдельно разблокирует группу своим
  офлайн-кодом восстановления. Код не сохраняется в localStorage, cookies,
  sessionStorage и Firestore. Выход/смена UID/ручная блокировка закрывают
  транспорт и делают следующие запросы недоступными. Проверка после
  асинхронного чтения не позволяет вернуть уже загруженные данные, если
  сеанс был закрыт в процессе. Это не удаляет возможные копии из памяти
  браузера, расширений, скачанных файлов или скриншотов.
- **e2ee/handover.js** — прототип передачи данных между устройствами через
  ECDH P-256 + HKDF-SHA256 + AES-256-GCM. Новый ответственный создаёт
  на своём устройстве временный закрытый ключ и передаёт только открытый
  запрос. Старый ответственный шифрует согласованный набор записей для этого
  запроса; новый расшифровывает пакет и **сам** генерирует новый AES-ключ
  группы и новый офлайн-код восстановления. Старый ключ не может
  расшифровывать новые записи, зашифрованные этим новым ключом.
- Новый ответственный должен безопасно сохранить новый код восстановления
  в отдельном защищённом месте. Секрет и открытый пакет восстановления
  нужны вместе. Исчезновение открытой страницы получателя до приёма
  пакета уничтожает возможность приёма — запрос придётся создать заново.
- **ECDH сам по себе не аутентифицирует отправителя.** Нужны проверка
  личности ответственных по независимому каналу и проверка отправленного
  пакета; приложение пока не реализует криптографически подтверждённую
  подпись отправителя. Атакующий может зашифровать ложные данные для
  публичного запроса получателя.
- Клиентский пакет передачи **не изменяет** Firebase-права, документы или
  group.custodianUid сам по себе. Сервер не должен переводить полномочия до того,
  как подтверждены согласованный полный снимок записей, резервная копия,
  новая запись recovery и целостность всего набора. Нужен протокол
  блокировки записи на время перехода и атомарной публикации либо
  безопасного восстановления после сбоя. В прототипе это не реализовано.
- Отзыв доступа не стирает старые шифротексты, исторические резервные
  копии и ранее просмотренный текст, доступный бывшему ответственному.
  Старый код восстановления нужно исключить из действующего хранения,
  но это не уничтожит полученные им ранее копии.
- Нужны ручная проверка протокола, анализ угроз, управление устройствами
  и отдельное разрешение на миграцию реальных данных. Никому не
  отправлять офлайн-коды, закрытые ключи и реальные списки через чат.

Проверки: tests/e2ee-session-handover.test.cjs (только вымышленные данные).

## Репетиция атомарного переключения ответственного (эмулятор)

Файл e2ee/emulator-cutover.mjs — **только для локального проекта
demo-s13-e2ee** и двух Firebase Emulator (Firestore/Auth). Код отвергает
любой другой projectId, нелокальный host, отсутствие переменных окружения
эмуляторов. Эмуляторный токен обхода правил **не существует в production**.
Этот код нельзя переносить в браузер или использовать с реальной базой.

Испытательная схема:

1. Действующий ответственный делает **отдельную восстановимую резервную
   копию** всех зашифрованных записей, а новый ответственный локально
   расшифровывает и проверяет переданный пакет. Личность обеих сторон
   подтверждается **вне приложения**.
2. Доверенный оператор переводит группу в состояние frozen условной
   записью, проверяющей версию документа. Все обычные клиентские
   изменения немедленно запрещаются правилами Firebase.
3. Проверяется полный набор документов четырёх поддерживаемых коллекций:
   cities, territories, publishers, addressMarkers. Новые зашифрованные
   документы должны иметь **те же уникальные пути**, что и старые.
   Отсутствующие, лишние, повторяющиеся и открытые документы отвергаются.
4. Проверяются поля зашифрованного нового пакета восстановления.
   Офлайн-код восстановления новому ответственному НЕ передаётся серверу.
5. **Одна атомарная Firestore commit** обновляет все зашифрованные
   документы, recovery/current и custodianUid, изменяет revision
   и возвращает status=active. Используются preconditions updateTime
   на каждом исходном документе, включая group metadata и recovery.
   При конфликте операция не выполняется; группа остаётся frozen,
   что предотвращает частичный перенос и требует разбора причины.
6. Пока переключения не произошло, оператор может отменить freeze
   с проверкой актуальной версии документа. После переключения старому
   ответственному сервер запрещает доступ, новый может расшифровывать
   всё новым ключом; при этом старые офлайн-копии **нельзя отозвать**.

Тест e2ee/test-cutover.mjs проверяет восстановление резервной копии,
блокировку изменений в frozen, отмену freeze, отсутствие документов,
ошибочный шифротекст, конфликт версий, атомарную замену,
права старого и нового ответственных и восстановление новым ключом.

**Ограничения:** это только сценарий для небольших групп — максимум
400 документов и не более 9 МБ запроса commit. Для групп большего
размера потребуется схема версий данных с атомарным переключением
активной версии. Утверждения backupRestored, recipientDecryptedAll,
identityVerifiedOutsideApp являются **внешними подтверждениями**
оператора, а не криптографическими доказательствами. Полную сверку
первоначального снимка с реальной базой обязан выполнять независимый
контроль; эмулятор не проверяет содержимое шифротекста. Сторонний
привилегированный администратор также может менять данные,
обходя client rules, что требует отдельной политики доверия.

Нет production-контроллера, безопасного управления доверенным
оператором и процессом согласования, защиты от атак на поставку JS,
полной проверки отказоустойчивости или схемы для больших групп.
**Настоящую Firebase и рабочий сайт этот этап не меняет.**

## Подготовка миграции и проверка резервной копии (этап 6)

Создан изолированный файл e2ee/migration-preflight.js, который **не
подключается к Firebase и не читает рабочие сведения**. Он принимает
переданную ему локальную копию документов, проводит предварительную
проверку и только затем создаёт зашифрованный архив для новой группы.

**Проверки до шифрования:**

- Для каждого документа нужен путь вида collection/documentId и тело
  из обычных JSON-типов. Firestore Timestamp, GeoPoint, DocumentReference,
  serverTimestamp и другие специальные значения нельзя молча превратить
  в строки — сначала нужна согласованная конвертация.
- Сверяются независимые количества документов по коллекциям cities,
  territories, publishers, addressMarkers. Это не доказывает, что
  независимый перечень сам был полным: его следует получать отдельно
  на согласованном моменте времени.
- Проверяются уникальность путей, имён возвещателей, номеров участков
  внутри города, связи участков с городами, допустимость дат,
  отсутствие пересечения выдач и правильность структуры истории.
  Если исходные данные не проходят проверку, миграция **останавливается**;
  никаких исправлений исходных данных автоматически не выполняется.
- Поддерживается только экспериментальный объём до 400 документов и
  8 МБ зашифрованного архива. Для крупных собраний понадобится
  отдельное решение с версиями/пакетами.

**Восстановление:** отдельный офлайн-код восстановления и зашифрованный
архив проверяются путём расшифровки и сравнения всех данных с исходным
локальным снимком. В архивах не содержатся имена или даты в открытом
виде, только имена коллекций, ID, шифротекст, размер/количество и
неподписанная контрольная сумма SHA-256. Эта сумма защищает от
случайной порчи, но **не доказывает подлинность архива** и не защищает
от отката к старой версии. Реальный бэкап должен храниться отдельно,
а офлайн-код — в другом месте. Открытый код не передавать в чат.

**Тест:** tests/e2ee-migration.test.cjs — только вымышленные данные,
без Firebase, производственной учётной записи и реальных файлов.

**Остаётся:** согласовать структуру маркеров адресов и административных
метаданных, обеспечить неизменяемый согласованный снимок рабочей
Firestore, проверить архив и копию восстановления на двух независимых
устройствах, согласовать поэтапное переключение и план возврата на
исходную версию. Нужна самостоятельная проверка безопасности.

## Ограничения безопасности

- **Это не готовая сертифицированная E2EE-система.** Реализованы отдельные
  прототипы блокировки сеанса и смены AES-ключа на устройстве получателя.
  Серверное переключение прав и атомарная замена маленького набора
  шифротекстов проверяются **только в эмуляторе**. Production-передача,
  безопасное хранение ключа при повседневной работе и аудит протокола
  не реализованы.
- Случайный recovery code — полноценный **секрет доступа**, а не пароль.
  Его нельзя отправлять через мессенджер, почту или в этот чат.
  Потеря и кода, и действующего устройства означает возможную окончательную
  потерю зашифрованных данных. Утечка кода **вместе с пакетом восстановления**
  раскрывает ключ группы.
- Firebase может видеть незашифрованные **метаданные**, например groupId,
  имя коллекции, ID документа и размеры/времена запросов. Нужно отдельно
  определить, какие именно поля подлежат шифрованию.
- E2EE не защищает от заражённого компьютера, расширений браузера,
  скомпрометированного кода сайта или атак на цепочку поставки.
  Особенно важно защитить публикацию JavaScript на GitHub Pages.
- Случайные 96-битные nonce **очень** снижают вероятность повтора, но не
  устраняют её математически; нужны лимиты использования и ротация.
- Шифрование с AAD не гарантирует защиту от **отката на старую запись**
  (replay/rollback). Нужна стратегия защищённой версии и целостности состояния.
- При E2EE обязательны Firebase Authentication и серверные Security Rules:
  проверка членства/прав **каждой** группы. Текущие правила рассчитаны
  на одного владельца, а не несколько групп.
- В приложении пока есть поиск, сортировка, транзакционные проверки истории
  и экспорт S-13 с **открытыми** данными. Все эти операции нужно адаптировать
  под клиентскую расшифровку до реального подключения E2EE.

## Процесс внедрения (без риска для действующей базы)

1. Согласовать классы персональных данных, права одного ответственного,
   порядок передачи должности и организационные требования.
2. Провести независимый review криптографического протокола и оценку угроз.
3. На синтетических данных проверить браузеры, резервный код, отказ,
   аварийное восстановление, поиск, выдачу/возврат и S-13.
4. Проверить экспериментальную схему групп и Security Rules на Firebase
   Emulator. Разработать выдачу полномочий и безопасный отзыв доступа;
   независимая проверка всей схемы обязательна перед production.
5. Сделать резервную копию действующей базы **вне публичного репозитория**;
   проверить восстановление. Реальную миграцию — только после согласования.
6. Перенести данные с проверкой числа и содержания записей; отдельно
   протестировать отмену миграции и сценарии потери ключей.
7. Лишь после успешных проверок и подтверждения ответственных публиковать
   E2EE-функциональность для реальных данных.
